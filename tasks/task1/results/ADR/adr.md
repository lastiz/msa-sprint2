# ADR. Поэтапное выделение сервиса бронирований Hotelio

### Название задачи
Начало перехода Hotelio от монолита к микросервисам по паттерну Strangler Fig.

### Автор
Дикунов М.А.

### Дата
30.09.2026

### Функциональные требования

| № | Действующие лица или системы | Use Case | Описание |
| :-: | :- | :- | :- |
| 1 | Пользователь | Создать бронирование | Передать пользователя, отель и необязательный промокод -> проверить пользователя, отель и отзывы -> определить скидку и цену -> сохранить бронирование. |
| 2 | Пользователь | Посмотреть бронирования | Передать запрос списка, при необходимости указать пользователя -> получить соответствующие бронирования. |
| 3 | Пользователь | Найти отель | Указать город -> получить список или топ по рейтингу -> открыть информацию об отеле. |
| 4 | Сервис бронирований, монолит | Выполнить проверки | Запросить данные в монолите -> проверить активность пользователя, доступность отеля, отзывы и применимость промокода. |
| 5 | Сервис истории бронирований | Сохранить историю бронирований | Получить событие о созданной брони -> проверить, не обработано ли оно ранее -> сохранить данные для аналитики в отдельной БД. |

### Нефункциональные требования

| № | Требование |
| :-: | :- |
| 1 | Выносить по одному модулю, сохраняя работу остального монолита. |
| 2 | Сохранить внешний REST API на первом этапе и проверить совместимость поведения регрессионными тестами. |
| 3 | Обеспечить независимые развёртывание и масштабирование нового сервиса, выделить ему собственную БД. |
| 4 | Ограничить время сетевых вызовов, собирать логи и метрики ошибок и задержек, предусмотреть откат. |
| 5 | Не терять подтверждённые бронирования при переносе данных и публикации событий. |
| 6 | Новую бизнес-логику писать в выделенном сервисе. В монолите выполнять только необходимые интеграционные изменения. |

### Решение

#### Текущее состояние и проблемы

Hotelio - Spring Boot-монолит с общей PostgreSQL. Пользователи, отели, бронирования, промокоды и отзывы развёртываются вместе. Это связывает релизы и не позволяет отдельно масштабировать нагруженный модуль. Универсальный REST API также затрудняет развитие клиентских сценариев без BFF.

Создание бронирования зависит от пользователей, отелей, промокодов и отзывов. Поэтому изменения в этом сценарии требуют проверки нескольких модулей, а выпуск новой функции связан с релизом всего приложения.

#### Первый сервис - бронирования

Первым выделяем **Booking Service**. Бронирование - основной бизнес-сценарий, для которого важны отдельные релизы и масштабирование при пиках. Перенос его данных также создаёт основу для истории бронирований и будущего личного кабинета.

В проекте уже предусмотрены подключение внешнего сервиса и gRPC-контракт бронирования. Это упрощает первый шаг миграции.

Отели или отзывы вынести проще, но бронирование позволит отдельно развивать основной бизнес-сценарий. Остальные модули пока оставляем в монолите и обращаемся к ним через REST API.

#### Промежуточная архитектура

Состояние до миграции показано на [диаграмме контекста](diagram/context.puml). Пользователь обращается к единому монолиту Hotelio.

На [диаграмме промежуточной архитектуры](diagram/to-be.puml) бронирования уже выделены в отдельный сервис. Монолит остаётся входной точкой, но передаёт ему и создание, и чтение бронирований.

| Компонент | Ответственность и взаимодействия |
| :- | :- |
| Монолит | Сохраняет публичный REST API. Передаёт создание и чтение бронирований новому сервису по gRPC. Пользователи, отели, промокоды и отзывы остаются в его БД. |
| Сервис бронирований | Выполняет проверки и расчёт цены, создаёт и возвращает бронирования из собственной PostgreSQL. Необходимые данные получает через REST API монолита. |
| Kafka | Передаёт события о созданных бронированиях сервису истории. Не участвует в проверках перед созданием бронирования. |
| Сервис истории | Сохраняет историю и данные для аналитики в отдельной БД. Повторное получение события не создаёт дубликат. |

Сохраняем Java / Spring Boot и PostgreSQL как знакомый команде стек. gRPC используем между монолитом и сервисом бронирований, REST - для обращения к оставшимся модулям, Kafka - для истории. Отдельный API Gateway на первом шаге не нужен, его роль в маршрутизации запросов выполняет монолит.

Для надёжной отправки событий используем outbox, таблицу исходящих событий в БД бронирований. Бронирование и событие сохраняются одной транзакцией. Затем событие отправляется в Kafka, при ошибке отправка повторяется. Сервис истории сохраняет результат и идентификатор обработанного события одной транзакцией.

#### План миграции Strangler Fig

1. **Проверить монолит.** Запустить приложение и БД, выполнить регрессионные тесты и сохранить [лог проверки](../test-log.txt).
2. **Подготовить сервис бронирований.** Создать отдельное приложение и БД, реализовать gRPC API и REST-вызовы к монолиту. Добавить проверки работоспособности, таймауты, логи и метрики. Пока все пользовательские запросы обслуживает монолит.
3. **Перенести данные.** Сделать резервную копию, временно остановить создание бронирований и дождаться завершения текущих запросов. Скопировать существующие бронирования с сохранением ID, сверить данные и настроить выдачу новых ID без пересечений.
4. **Переключить запросы.** Направить создание и чтение бронирований из монолита в новый сервис по gRPC. После переключения только новый сервис работает с данными бронирований. Повторить тесты, проверить старые и новые записи.
5. **Подключить историю.** Добавить outbox и публикацию событий в Kafka. Запустить сервис истории, проверить сохранение событий и защиту от дубликатов.
6. **Завершить переход.** После проверки стабильности удалить старую логику и таблицу бронирований из монолита. Новые функции бронирования разрабатывать только в выделенном сервисе.

**Откат:** до появления новых записей можно вернуть запросы в монолит. После создания бронирований в новой БД сначала нужно остановить запись и перенести новые данные обратно, иначе они будут потеряны для старой системы.

В ближайшей перспективе получаем выделенное бронирование и отдельную историю, оставляя другие домены в монолите. Далее - последовательный вынос остальных модулей и развитие CI/CD, service mesh.

### Альтернативы

| Вариант | Преимущества | Почему не выбран первым |
| :- | :- | :- |
| Сначала выделить отели | Самостоятельный модуль, полезен для масштабирования поиска | Бронирования всё равно останутся связаны с релизами монолита. |
| Сначала выделить отзывы | Небольшой модуль, который проще перенести | Не даёт отдельного развития основного сценария бронирования. |
| Остаться на модульном монолите | Проще сопровождать инфраструктуру | Не позволяет независимо выпускать и масштабировать сервисы. |
| Переписать всё сразу | Единая новая архитектура без длительного перехода | Слишком большой объём и риск для маленькой команды, сложное переключение и откат. |

### Недостатки, ограничения, риски

| Риск | Как ограничить |
| :- | :- |
| Сетевые вызовы могут замедлять бронирование или завершаться ошибкой | Настроить таймауты и circuit breaker, который временно прекращает вызовы недоступного сервиса. Без обязательных проверок бронирование не создавать. |
| Потеря данных или некорректный откат | Резервная копия, один владелец записи, сверка переноса и обратный перенос новых данных при откате. |
| Событие не отправлено или получено повторно | Хранить события в outbox, повторять отправку и проверять ID обработанных событий в сервисе истории. |
| Команде нужно сопровождать больше приложений и БД | Вводить изменения последовательно, проверять их тестами и наблюдать за ошибками и задержками. |
